# Emulator documentation comparison

This report is for Nestlin maintainers deciding which user, developer, release, and agent documentation practices are worth adopting from mature emulator projects.

**Research date:** 2026-09-14

**Scope:** Nestlin compared with RPCS3, Dolphin Emulator, PCSX2, and MAME. Only first-party repositories, project documentation, contribution guides, templates, and CI configuration were used. “Observed” statements describe those sources as reviewed; “Recommendations” are proposals for Nestlin, not claims about an external standard.

**Nestlin baseline:** Documentation tracked at `HEAD` when the audit began. Untracked documentation drafts created concurrently in the worktree were excluded.

## Executive finding

Nestlin already has unusually strong emulator-specific test documentation and detailed mapper implementation notes. Its main weakness is not lack of technical knowledge, but lack of a maintained public documentation system around that knowledge. The user path stops at building from source; support and troubleshooting are undefined; contributor policy is brief; architecture is split between agent instructions, a narrow glossary, and historical plans; and documentation has no automated quality gate.

The most urgent problem is factual drift. The [README](../../README.md) says “12 mappers” and lists 12, while [MAPPER_SUPPORT.md](../../MAPPER_SUPPORT.md) currently contains 31 mapper status sections (plus battery-save coverage). A concise document that is wrong is less useful than a detailed one that is hard to navigate.

The mature projects do not share one perfect structure. Their repeatable practices are: route each audience to a dedicated path; define what belongs in support versus the issue tracker; require reproducible evidence; publish compatibility in a user-readable taxonomy; state emulator-specific legal boundaries; keep contributor expectations explicit; and make documentation buildable or mechanically checked.

## Observed practices in the comparison projects

| Area | Observed first-party practice | Relevant lesson for a small NES emulator |
|---|---|---|
| User onboarding | RPCS3 routes users from its repository to a dedicated Quickstart and compatibility/support channels ([README](https://github.com/RPCS3/rpcs3/blob/master/README.md), [contribution entry point](https://github.com/RPCS3/rpcs3/blob/master/.github/CONTRIBUTING.md)). PCSX2’s official docs are explicitly divided into setup, configuration, troubleshooting, advanced, and contributing sections ([docs overview](https://pcsx2.net/docs/)); its running guide distinguishes stable and nightly builds and gives per-OS installation steps ([running guide](https://pcsx2.net/docs/setup/running/)). Dolphin’s README states supported hosts and links the FAQ before use, while its guide index covers game dumping, controllers, performance, storage, and diagnostics ([README](https://github.com/dolphin-emu/dolphin/blob/master/Readme.md), [guides](https://dolphin-emu.org/docs/guides/)). | A README should orient and route. Detailed setup and first-run material should have a stable user-facing home rather than being mixed with developer commands.
| Compatibility and support | RPCS3 publishes named compatibility states with definitions (Playable, Ingame, Intro, Loadable, Nothing) and links entries to game-specific information ([compatibility list](https://www.rpcs3.net/compatibility)). Its issue chooser disables blank issues and routes setup help and compatibility reports elsewhere ([chooser config](https://github.com/RPCS3/rpcs3/blob/master/.github/ISSUE_TEMPLATE/config.yml)). PCSX2 likewise links a tested-title compatibility list from its README and separates general help from bug reporting ([README](https://github.com/PCSX2/pcsx2/blob/master/README.md), [general troubleshooting](https://pcsx2.net/docs/troubleshooting/general/)). MAME distinguishes released-version user bugs, developer-facing issues, and support/discussion ([contributing guide](https://docs.mamedev.org/contributing/), [issue chooser](https://github.com/mamedev/mame/blob/master/.github/ISSUE_TEMPLATE/config.yml)). | Define status terms and reporting boundaries. Mapper support is not the same as per-game compatibility, and “working” needs a stated evidence level and known limitations.
| Troubleshooting and actionable reports | RPCS3’s bug form requires a log and explains exactly where to find it on each OS; its separate regression form requires the last good and first bad builds plus logs from both ([bug form](https://github.com/RPCS3/rpcs3/blob/master/.github/ISSUE_TEMPLATE/2-bug-report.yml), [regression form](https://github.com/RPCS3/rpcs3/blob/master/.github/ISSUE_TEMPLATE/1-regression-report.yml)). PCSX2 documents collection of `emulog.txt`, graphics dumps, and regression bisection before routing users to support or issues ([diagnosing and reporting](https://pcsx2.net/docs/troubleshooting/identify/)). MAME’s form asks for exact version, environment, emulated system/software, incorrect and expected behaviour, reproduction steps, and original-hardware evidence where possible ([bug form](https://github.com/mamedev/mame/blob/master/.github/ISSUE_TEMPLATE/bug-report.yml)). | Troubleshooting should produce a portable evidence bundle: Nestlin version, ROM identity without copyrighted content, mapper/header data, host/JDK, non-default settings, logs, exact steps, expected result, and an FM2/save-state/screenshot where appropriate.
| Developer and architecture documentation | MAME puts user manuals, debugger/tooling material, contribution guidance, and deep technical specifications in one navigable documentation set ([documentation index source](https://github.com/mamedev/mame/blob/master/docs/source/index.rst), [technical specifications](https://docs.mamedev.org/techspecs/)). Dolphin keeps focused technical documents beside source, including storage formats and device interfaces ([WIA/RVZ format](https://github.com/dolphin-emu/dolphin/blob/master/docs/WiaAndRvz.md), [device IOCTLs](https://github.com/dolphin-emu/dolphin/blob/master/docs/DolphinDeviceIOCTLs.md)). RPCS3’s developer page is primarily a curated hardware-reference compendium rather than a full codebase architecture guide ([developer information](https://github.com/RPCS3/rpcs3/wiki/Developer-Information)). | Keep project architecture, hardware references, and historical design records distinct. An explicit current-state architecture map is valuable even when source-level details remain close to code.
| Testing and contribution workflow | MAME asks contributors to build and test locally, recommends debug builds, and explains commit/PR expectations and emulator-specific test evidence ([contributing guide](https://docs.mamedev.org/contributing/)). PCSX2’s contribution guide covers quality, build entry points, formatting, commit messages, and PR conduct ([contribution guide](https://pcsx2.net/docs/contributing/)); its PR template asks for change description, rationale, suggested tests, and AI use ([PR template](https://github.com/PCSX2/pcsx2/blob/master/.github/PULL_REQUEST_TEMPLATE.md)). Dolphin documents a pinned formatter and an opt-in pre-commit lint hook ([contributing guide](https://github.com/dolphin-emu/dolphin/blob/master/Contributing.md), [lint script](https://github.com/dolphin-emu/dolphin/blob/master/Tools/lint.sh)). | Put the minimum merge contract in `CONTRIBUTING.md`, make test evidence visible in the PR template, and keep optional local hooks consistent with authoritative CI.
| Release, security, and legal | PCSX2 clearly states that a BIOS dumped from a legitimately owned console is required ([README](https://github.com/PCSX2/pcsx2/blob/master/README.md)). Dolphin’s contributor policy explicitly covers trade secrets, piracy, contribution licensing, and AI-assisted work ([contributing guide](https://github.com/dolphin-emu/dolphin/blob/master/Contributing.md)). MAME publishes both licensing detail and an explicit security posture warning not to run elevated ([license](https://docs.mamedev.org/license.html), [security concerns](https://docs.mamedev.org/security.html)). PCSX2 documents stable versus nightly release expectations ([running guide](https://pcsx2.net/docs/setup/running/)). | Emulator documentation needs a ROM/legal statement, contribution provenance rules, a vulnerability-reporting route, safe-use guidance for untrusted files, and an explicit release/support policy.
| Agent guidance | PCSX2 has repository-level agent instructions covering structure, build/format commands, contribution rules, mandatory AI disclosure, human responsibility, and restrictions on automated posting ([AGENTS.md](https://github.com/PCSX2/pcsx2/blob/master/AGENTS.md)). RPCS3 and Dolphin also put human ownership and AI disclosure or restrictions into public contributor policy ([RPCS3 README](https://github.com/RPCS3/rpcs3/blob/master/README.md), [Dolphin contributing guide](https://github.com/dolphin-emu/dolphin/blob/master/Contributing.md)). | Agent instructions should point to the same public source of truth as human instructions and should require documentation-impact review, verification, and disclosure rather than becoming a private replacement for contributor docs.
| Documentation automation | MAME stores Sphinx sources in the repository and runs a docs-only CI workflow on pushes and pull requests; it builds both HTML and PDF and uploads both artifacts ([docs workflow](https://github.com/mamedev/mame/blob/master/.github/workflows/docs.yml)). PCSX2 validates its structured GameDB in a dedicated workflow ([GameDB workflow](https://github.com/PCSX2/pcsx2/blob/master/.github/workflows/lint_gamedb.yml)). | For Nestlin, a full docs site is optional; link, style, spelling, and generated-status consistency checks are the higher-value first step.

## Nestlin documentation audit (observed)

| Area | What exists | Concrete gap or risk |
|---|---|---|
| User onboarding | The [README](../../README.md) explains requirements, source builds, command-line flags, controls, ROM formats, and configuration paths. | No download/install path for ordinary users, first-run walkthrough, platform-specific JavaFX/JInput guidance, update/uninstall guidance, or clear “where files are stored” reference. It assumes source checkout and Gradle familiarity.
| Compatibility/support | [MAPPER_SUPPORT.md](../../MAPPER_SUPPORT.md) is highly detailed and records known games, implementation notes, tests, and limitations. | README and mapper inventory disagree. Mapper-level “Working” is not defined as a user compatibility guarantee; there is no compact tested-game view, evidence/date convention, support channel, supported-build policy, or issue-reporting route.
| Troubleshooting | `bootcheck`, `diverge`, replay, Mesen2 comparison, and test-environment diagnostics are documented in [CLAUDE.md](../../CLAUDE.md) and partly in the README/testing guide. | The strongest diagnostics are agent/developer-facing. There is no user troubleshooting decision tree for black screens, bad dumps/headers, audio, input/JInput, saves, archives, Java/JVM failures, or collecting a safe report bundle.
| Architecture | [CLAUDE.md](../../CLAUDE.md) has a useful package map and invariants; [CONTEXT.md](../../CONTEXT.md) is a domain glossary; three [ADRs](../adr/) record selected design decisions. | Public docs lack a current end-to-end architecture narrative (CPU/PPU/APU clocking, buses and DMA, mapper seam, run/UI threads, persistence boundaries, and diagnostic seams). `CONTEXT.md` mixes implemented and explicitly forward-looking terms, and crucial knowledge is concentrated in agent context.
| Testing | [TESTING_STRATEGY.md](../TESTING_STRATEGY.md) documents the oracle model, test pyramid, anti-patterns, and recipes in depth. Build logic uses tag-driven test lanes, and CI runs builds/tests. | The guide still labels itself “Proposal for review” and contains historical migration/open-question sections even though much of the design is now policy. The quick contributor contract does not map change types to required lanes or explain expected skips in one compact table.
| Contribution workflow | README has a four-item minimum bar and links mapper guidance. Agent-specific skills and hooks encode additional practices. | There is no `CONTRIBUTING.md`, Code of Conduct, review process, commit/PR guidance, documentation policy, provenance/legal guidance, or public AI policy. Human and agent expectations can diverge.
| Release/security/legal | MIT license, rcheevos license/notice, native-library build/distribution notes, and native release workflows exist. | There is no application release process, versioning/changelog policy, supported-platform artifact matrix, checksum/signing guidance, save-state compatibility policy, `SECURITY.md`, vulnerability contact, untrusted-ROM/archive threat statement, privacy summary for RetroAchievements, or explicit “ROMs are not provided; use lawful dumps” notice.
| Templates/automation | Four GitHub Actions workflows build/test and release native RA libraries. Existing test lints enforce some code/test/mapper invariants. | No issue forms, PR template, documentation-specific workflow, Markdown style/spelling/link check, or automated check that public compatibility claims match code and `MAPPER_SUPPORT.md`.
| Information lifecycle | Historical plans are retained and the README points to selected active documents. | `docs/` does not visibly separate active guides, architecture decisions, research, and archived plans. Stale status labels and duplicate facts make ownership unclear.

## Recommendations for Nestlin

These are recommendations derived from the observations above.

### P0 — restore trust and create a public front door

1. **Eliminate compatibility drift.** Remove the hard-coded mapper count/list from README or generate it from one canonical machine-readable table. Keep README to a short support summary; reshape `MAPPER_SUPPORT.md` into a compact user matrix (status, evidence date, known limits, tested titles) linking to per-mapper developer notes. Define statuses such as `Implemented`, `Boot-tested`, `Oracle-verified`, `Playable`, `Partial`, and `Stub`.
2. **Add a user path.** Create `docs/user/getting-started.md`, `configuration-and-files.md`, and `troubleshooting.md`. Cover supported platforms, JDK/runtime expectations, install/build choices, lawful ROM acquisition language, first launch, loading a game, controls, save locations, common failures, and how to collect diagnostics. Keep README as the two-minute path into these pages.
3. **Add the community contract.** Add `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, and `SECURITY.md`. `CONTRIBUTING.md` should state supported change types, build/test commands, regression-test expectations, ROM/privacy rules, documentation duties, review flow, and AI/provenance policy. `SECURITY.md` should distinguish private vulnerability reports from ordinary bugs and warn that ROMs, archives, save states, and movie files are untrusted inputs.
4. **Add structured intake.** Create separate GitHub forms for emulation bug, application/UI bug, regression, and feature request; disable blank issues and route support appropriately. Require Nestlin version/commit, OS/JDK, ROM hash plus mapper/header output (never the ROM), default/non-default settings, exact reproduction steps, expected/actual result, and safe attachments. Add a PR template with rationale, linked issue, test evidence, compatibility/docs impact, screenshots where relevant, and AI assistance disclosure.

### P1 — publish how the emulator works and how it changes

5. **Create `docs/development/architecture.md`.** Document the cycle/timing model, CPU and PPU buses, DMA/interrupt ownership, mapper interface, APU/audio pipeline, UI versus emulation thread boundaries, save-state/save-RAM ownership, and the test seams. Link to ADRs for decisions and to external hardware references for hardware facts; do not make `CLAUDE.md` the only architecture entry point.
6. **Turn testing strategy into current policy.** Replace the proposal/migration framing in `TESTING_STRATEGY.md` with a short current-state overview, a change-type-to-test-lane matrix, fixture/ROM rules, expected skip semantics, diagnostic recipes, and CI parity commands. Move completed migration history to an archived decision note.
7. **Document releases.** Add `docs/maintainers/releasing.md` covering versioning, changelog/release-note generation, per-platform artifacts, native RA assets/manifests, checksums, smoke tests, save-state compatibility/migration, rollback, and which versions receive support. Publish a user-visible changelog or release notes and distinguish source builds from supported releases.
8. **Clarify legal and privacy boundaries.** Add a short legal section to README/getting-started: no commercial ROMs are distributed; users must supply lawfully obtained dumps; bug reports must not attach ROMs; no leaked/confidential material should be used; explain RetroAchievements network/credential behaviour and link the vendored notices.

### P1 — make documentation a maintained artifact

9. **Add a docs CI job.** On Markdown/config changes, run a pinned Markdown style check, internal/external link check, and spelling/terminology check. Add a repository-specific validator that compares mapper dispatch with the canonical compatibility data. CI must be authoritative; an opt-in pre-commit hook should run the same fast checks on changed files.
10. **Define documentation ownership rules.** In `CONTRIBUTING.md` and agent instructions, require a docs-impact check whenever UI, CLI, config, supported formats/mappers, test commands, persistence, security/privacy, or release behaviour changes. Require links to be relative where possible, commands to be executable, claims to name their evidence, and current facts to be separated from proposals/history.
11. **Improve agent guidance without duplicating policy.** Expand `AGENTS.md` beyond its current one-line pointer so agents must read the public contributor/testing/architecture docs, update user docs in the same change, run docs checks, avoid publishing copyrighted ROM data or secrets, disclose AI assistance, and report skipped verification. Keep detailed machine-local paths in ignored local context. Prefer one shared policy source referenced by both `AGENTS.md` and `CLAUDE.md` over two copies.

### P2 — reduce and archive

12. **Give `docs/` an index and lifecycle.** Add `docs/README.md` grouping user guides, developer guides, ADRs, research, and archived plans. Move completed milestone plans such as `PPU_RENDERING_PLAN.md` and `DONKEY_KONG_RENDERING_PLAN.md` under `docs/archive/` (or add conspicuous status/supersession headers). Mark forward-looking glossary entries as proposals or move them to the relevant ADR.
13. **Remove duplicated volatile facts.** Counts, supported-mapper lists, version numbers, platform matrices, and command inventories should each have one owner. Other pages should summarize and link. The 1,200-line mapper document should retain evidence, but historical debugging narratives that no longer help users should move to ADRs/research notes or git history.

## Proposed minimum documentation standard

A change should not be considered complete when it changes observable behaviour without updating its owning document. The minimum maintained set should be:

- `README.md`: purpose, maturity, quick start, supported platforms/formats at a summary level, legal note, and links.
- `docs/user/`: getting started, controls/config/files, compatibility semantics, troubleshooting/report collection.
- `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`: contribution, community, provenance, reporting, and security contracts.
- `docs/development/architecture.md`, current testing strategy, ADRs: present architecture, verification, and durable decisions.
- `docs/maintainers/releasing.md` plus changelog/release notes: reproducible release and support policy.
- Structured issue forms and PR template: mandatory reproducibility, testing, documentation impact, and AI disclosure fields.
- CI: Markdown/style, spelling, links, and consistency checks, with the same fast command available through an optional local hook.

This is intentionally smaller than MAME’s publishing system. It adopts the mature projects’ information architecture and evidence discipline without imposing a documentation website before Nestlin needs one.
